# Удалённый SQL Server

[← README](../README.md)

`Setup.ps1` автоматизирует локальный SQL: он создаёт логин вида `IIS APPPOOL\IISReportsSimple`. Такой локальный виртуальный аккаунт нельзя переносить на другой SQL-сервер.

Для удалённого SQL используйте ручную установку:

1. Администратор SQL создаёт отдельную базу и выполняет **целиком, в ней** `sql/001-v3-schema.sql`, затем `sql/005-auto-sources.sql`. На существующей базе ir3 история сохраняется.
2. DBA создаёт отдельный SQL-логин/пользователя приложения либо предоставляет доступ корректной доменной служебной учётной записи.
3. Пользователю в этой базе достаточно `CONNECT` и `SELECT, INSERT, UPDATE, DELETE` на схему `ir3`. Не выдавайте приложению sysadmin/db_owner.
4. Создайте в IIS отдельный пул CLR v4.0 / Integrated и сайт с физическим путём к **содержимому `web/`**. Не публикуйте `sql`, `tests` или установщик.
5. В рабочем `Web.config` укажите `ConnStr` для реального SQL-сервера. Параметры сервера, порта, SQL-логина и пароля выдаёт DBA. Не добавляйте Integrated Security при SQL-аутентификации.
6. Выдайте пулу чтение веб-каталога и журналов. `LogRoots` содержит корни локальных файлов на машине IIS, а не на SQL-сервере.
7. Откройте локальную панель и `Reports.ashx?action=diag`.

Для SQL-аутентификации строка обычно имеет поля:

```text
Data Source=tcp:ИМЯ_SQL_СЕРВЕРА,ПОРТ;Initial Catalog=IISReports;User ID=ЛОГИН_ПРИЛОЖЕНИЯ;Password=ПАРОЛЬ;Encrypt=True;TrustServerCertificate=False;
```

Это описание формата, **не готовая строка для вставки**. Символы пароля должны быть экранированы по правилам connection string и XML. Не публикуйте реальные пароли в репозитории или сообщениях.

При Windows-аутентификации удалённого SQL настройку доменного аккаунта и делегирования выполняет администратор. Не включайте ASP.NET impersonation только для обхода ошибки логина.

Доверие к сертификату SQL настраивается на компьютере IIS. HTTPS-сертификат панели это не заменяет.
