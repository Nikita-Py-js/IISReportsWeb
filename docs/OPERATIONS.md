# Эксплуатация

[← README](../README.md)

## Повседневная проверка

```powershell
Get-Service IISReportsAgentV3
Get-Content 'C:\Services\IISReportsAgentV3\logs\agent-*.log' -Tail 50
```

В панели смотрите Health, Сборщик, Источники, Задания/доставка, Инциденты. `healthy`, heartbeat и отсутствие LastError — разные показатели. Зелёный процесс Windows не гарантирует SQL-связность или полноту импорта.

Частота сканирования задаётся конфигом агента. Работа последовательная: длинный импорт/проверка может задержать следующий цикл. Это не система жёсткого real-time SLA.

## Источники, Verify, Replay, новая generation

**Обычный Scan** дочитывает журналы от сохранённой позиции. Данные и checkpoint фиксируются порциями в транзакции. Незавершённая строка в конце откладывается.

**Verify** сравнивает сохранённые контрольные суммы импортированных диапазонов с файлом. Это проверка сохранённого содержимого, а не подтверждение, что IIS никогда не терял события до записи журнала.

**Replay** повторяет разбор активного поколения с проверкой целостности. Идентификатором является пара поколения и байтового смещения, поэтому одинаковые реальные строки на разных позициях не склеиваются.

**New generation** используется для намеренно заменённого/обрезанного файла. Старые строки не удаляются, но представление CurrentRequests выбирает активное поколение. Поэтому текущие графики могут уменьшиться или измениться — это не физическое удаление старой истории.

Не удаляйте `ir3.Files`, `Generations`, `RawEvents`, `ImportChunks` вручную для обхода ошибки. Карантин содержит исходную строку и причину; это предпочтительнее молчаливого пропуска.

## Проверки сайтов и правила

Разрешите нужные адреса в обоих конфигах, затем создавайте проверки через UI. Используйте внутренние специально предназначенные health endpoints без побочных эффектов; проект выполняет GET и не передаёт учётные данные.

Поддерживаемые метрики правил:
```text
5xx_count, 5xx_percent, p95_ms, auth_failures, requests, import_stale_minutes
```

Порог, минимальное число образцов, последовательные нарушения и восстановления задаются в редакторе. Пример: 5xx > 5% за 5 минут при минимум 100 запросах, FailAfter=3. Детали сравнения и выборки определяются кодом `V3Monitoring.cs`; это не обученная система поиска аномалий.

Инциденты группируются по объекту правила/проверки. Оператор может подтвердить/закрыть инцидент; восстановление фиксируется отдельно.

Поскольку правила вычисляет **сам агент**, он не сможет отправить уведомление о своём полном прекращении работы. Health/heartbeat нужно контролировать внешней системой.

## Доставка

Используется отдельный JSON-webhook, очередь в SQL, retries и журнал результата. Доставка может повториться, принимающая система должна дедуплицировать `eventId`. Перед включением URL проверьте старую очередь: ожидающие события могут быть доставлены.

Не публикуйте `WebhookUrl`, если секрет включён в query/path. При изменении agent-config перезапустите службу.

## Резервные копии

Резервируйте базу SQL, закрытые runtime-конфиги, sources-настройки, `sites.json`, файлы обогащения, исходные журналы, сертификаты согласно принятой политике ключей. Сырые `.log` не восстанавливают настроенные проверки, правила и инциденты без SQL-backup.

Проверяйте восстановление на отдельном стенде. Для SQL Express при отсутствии SQL Agent используйте утверждённое администратором расписание резервного копирования, например через Планировщик Windows. Собственный сборщик не выполняет SQL-backup.

Автоматического retention нет. Контролируйте рост БД, транзакционного журнала и файлов `logs` службы. Не удаляйте историю без отдельной политики и проверенного скрипта обслуживания.

## Остановка и удаление

Для обслуживания сначала остановите службу, затем отдельный пул IIS. SQL при обычном обновлении остаётся работать.

Для полного удаления **после backup** можно остановить/удалить службу, удалить только выделенный сайт и пул через IIS Manager и архивировать папки. База не удаляется автоматически. Не запускайте команды удаления для Default Web Site, общих пулов или общей базы.

При нескольких установках на разных серверах имена могут повторяться, но используйте отдельные БД. В одной БД разрешён только один активный агент; блокировка не предназначена для горизонтального распределения сбора.

## Выбор мониторинга и обнаружение

В 3.1.1 ежедневная эксплуатация не требует `Register-LogSource.ps1`. Задача IISReports-DiscoverSites обновляет снимок, агент добавляет новые сайты по умолчанию включёнными. В «Источниках» можно снять флажки и нажать «Сохранить выбор».

Отключение влияет только на импорт. Глобальные правила алертов продолжают выполняться по своим настройкам и могут учитывать исторические записи в окне; это не эквивалент отключения правил/активных проверок. Удаление истории и политика хранения настраиваются отдельно, автоматической очистки при снятии флажка нет.

Контролируйте отдельно задачу обнаружения и Windows-службу. После перезагрузки задача стартует сама, агент читает свежий снимок. При длительной остановке задачи журналируйте ошибку, а не пытайтесь исправлять её очисткой SQL.

Перед удалением проекта остановите/удалите задачу, остановите службу и сохраните БД. Удаление/отзыв добавленных ACL с каталогов IIS требует отдельного решения администратора; выключение источника их не отзывает.
